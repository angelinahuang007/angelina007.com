Real-time Systems Design

Understand core real-time system patterns: frame budgets, buffering strategies, game loops, and thread architectures. Interactive diagrams show how timing constraints shape system design.

Frame Timing & Budget

Target FPS: 60
Frame Budget: At 60 FPS, you have 16.67ms to update physics, render, and display. Each phase (Update, Physics, Render) must fit within this window. Exceeding it causes frame drops visible to players.

Buffering: Double vs Triple

Double Buffering: Front buffer (displayed), back buffer (being rendered). After render, buffers swap. Risk: long renders delay display.

Triple Buffering: Three buffers allow GPU to work while CPU renders, reducing stalls. Trade-off: one frame of input latency.

Game Loop Patterns

Fixed Timestep: Update at constant dt (e.g., 16.67ms). Physics is deterministic. May render multiple times per update or skip frames.

Variable Timestep: dt = frame delta time. Render matches frame rate. Physics less stable with large deltas.

Semi-Fixed: Update fixed timesteps multiple times per frame, render once. Best of both: stable physics + smooth visuals.

Thread Architecture

Typical Layout: Main thread handles game logic, physics, and input. Render thread prepares GPU commands (single-threaded in most engines). Worker threads handle physics simulation, audio, network I/O in parallel. Thread synchronization at frame boundaries prevents race conditions.
